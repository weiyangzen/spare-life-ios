# Spare Life Blueprint

## 1. 产品定义

Spare Life 的核心不是一个普通聊天 App，而是一个 `human-agent-agent-human` 社交系统：

1. 用户先表达意图。
2. 用户分身先去试探、筛选、暖场、谈条件。
3. 对方分身先响应、过滤、协商、建立信任。
4. 当双方进入高意图阶段，再把真人拉进来。
5. 建立关系后，由真人和双方分身共同维护关系。

这个定位决定了 5 个底部导航的职责分工：

| Tab | 角色定位 | 核心对象 | 主要目标 |
| --- | --- | --- | --- |
| 咸虾 | 扫码进入现实场景的社交雷达 | 附近话题、现场观点、围观人群分身 | 看大家都在说什么，快速进入场景社交 |
| 大师 | 专家分身馆 | 各领域大师分身 | 问建议、做陪聊、做决策辅助 |
| 赚闲能 | 陌生社交主战场 | 陌生人分身、陌生人真人 | 闲置物品、技能问答、婚恋、交友、求职招人、跑腿求助 |
| 消息 | 熟人关系主场 | 好友、熟人、双方分身 | 长期聊天、双人陪伴、多人共玩 |
| 我的 | 分身养成与控制台 | 自己、自己的分身 | 同步度、人格、记忆、统计、隐私 |

## 2. 创意策划案到页面的信息架构映射

### 2.1 咸虾

主要吸收创意来源：

- 方向4 社交地图探索
- 方向11 意图识别与匹配引擎

### 2.2 大师

主要吸收创意来源：

- 方向5 人格 DNA 编码系统
- 方向6 记忆宫殿架构
- 方向13 技能交易市场
- 方向17 跨时态 mentorship

### 2.3 赚闲能

这一页不再按抽象创意方向组织，而是按 6 条可比较的 `A2A 产品赛道` 组织：

- 闲置物品买卖 A2A
  - 类比 `咸鱼`，重点是买卖双方分身先问价、验货、议价、筛掉低质量沟通。
- 技能问答撮合 A2A
  - 类比 `evomap`，重点是提问者和技能提供者分身先对齐问题范围、难度、交付方式。
- 婚恋匹配 A2A
  - 重点是男女匹配、价值观预筛、边界预沟通、见面前预热。
- 交友匹配 A2A
  - 类比 `Soul`，重点是兴趣、情绪、人格、聊天氛围的先匹配后见人。
- 求职招人 A2A
  - 类比 `Boss直聘`，重点是候选人与招聘方分身先完成岗位匹配、履历解释、需求澄清。
- 跑腿求助应答 A2A
  - 类比 `RentAHuman`，重点是发布需求、快速响应、条件确认、任务接单。

底层仍可吸收这些创意方向作为实现能力，但不再作为一级信息架构：

- 方向2 社交能量经济
- 方向3 A2A 竞技场
- 方向11 意图识别与匹配引擎
- 方向14 交易撮合佣金
- 方向15 A2A 协议栈与多智能体协作

### 2.4 消息

主要吸收创意来源：

- 方向6 记忆宫殿架构
- 方向7 情感波动引擎
- 方向8 社交人格面具系统

页面组织原则：

- 这一页首页是 `类似 IM 的消息列表`，不是陌生社交广场。
- 最上方是最近聊天或最近活跃联系人。
- 点进某个人之后，再把会话中的摘要、关系状态、对人面具、待回应主题做卡片化。
- 这里重点是 `对不同人调整面具`、`情绪连续性`、`记忆连续性`，不是把方向9/10当成一级玩法入口。

### 2.5 我的

主要吸收创意来源：

- 方向1 分身觉醒度系统
- 方向5 人格 DNA 编码系统
- 方向6 记忆宫殿架构
- 方向7 情感波动引擎
- 方向8 社交人格面具系统

## 2.6 页面信息组织总规范

整体不走传统 iOS 工具型列表页，也不走后台 dashboard 风格。`咸虾 / 大师 / 赚闲能 / 我的` 的首页统一采用类似小红书的双列瀑布流卡片逻辑；`消息` 首页保留 IM 结构，但进入单人会话后再卡片化组织。

UI 技术强约束：

- iOS 客户端页面层默认采用 `SwiftUI`。
- 如遇到现有旧式 UI 技术或 UIKit 承载页面，需要按新 UI 标准迁移到 `SwiftUI` 的页面结构、状态流和交互承接，不再继续新增旧式 UI 页面。
- 可以在必要场景保留极少量平台桥接层，但页面主体、信息架构和交互层不应继续以 UIKit 作为长期标准。

统一要求：

- `咸虾 / 大师 / 赚闲能 / 我的` 首页默认都是 `双列瀑布流卡片流`。
- `消息` 首页默认是 `IM 风格消息列表 + 最近聊天区`，不是瀑布流首页。
- 卡片高度允许不一致，内容密度由卡片类型决定，避免所有模块等高导致信息发散。
- 首页首屏必须先给用户“可逛”的感觉，而不是“可填表”的感觉。
- 顶部允许有固定功能条，但固定区只放高频控件，不把大量信息堆在顶部。
- 每张卡片只承载一个主目标，例如继续聊、发起破冰、查看摘要、调整同步度，不做多 CTA 堆叠。
- 卡片流中的内容排序优先级默认由 `相关性 + 新鲜度 + 社交价值 + 当前状态` 共同决定。
- 卡片必须支持快速预览，用户不点详情也能理解大意。
- 卡片必须支持轻操作，例如喜欢、略过、收藏、隐藏、继续聊、让分身先聊。
- 每个 Tab 都需要记住自己的滚动位置、筛选状态和上次浏览上下文。
- 首层信息组织强调发现和浏览，复杂编辑动作下沉到详情页、sheet 或二级页。

统一页面骨架：

1. 顶部导航区：标题、搜索、筛选、切换器、必要的全局操作。
2. 顶部轻量级固定模块：例如最近聊过谁、闲能余额、同步度、扫码入口。
3. 主内容区：瀑布流卡片，或消息页中的 IM 列表。
4. 详情页：承接深度内容、复杂操作和完整线程。
5. 全局底部导航：5 个 Tab 固定驻留，中间黄色大按钮是“赚闲能”。

统一卡片类型建议：

- 摘要卡：场景摘要、会话摘要、关系摘要、周报摘要。
- 人物卡：大师卡、分身卡、熟人关系卡、公开 profile 卡。
- 行动卡：继续聊、发起破冰、加入会诊、完成任务、赚闲能。
- 状态卡：同步度、觉醒度、情绪状态、羁绊进度、数据库状态。
- 事件卡：领域事件、竞技场活动、关系纪念日、待处理提醒。
- 内容卡：热评、观点、战报、回忆片段、成长日记。

设计约束：

- 不允许把任一首页做成“全是纯文字列表项”的弱视觉结构。
- 不允许把“我的”退化成普通设置页；它应该是分身控制台的卡片流。
- `消息` 首页可以是传统 IM 语义的会话列表，但需要有顶部最近聊天和更强的状态摘要。
- 不允许把“消息”会话详情页退化成纯气泡时间线；对人面具、关系摘要、情绪状态、待回应主题必须卡片化呈现。
- 详情页可以采用聊天时间线、表单、图表、编辑器，但首页层必须优先卡片流。

## 3. 底部导航详细蓝图

## 3.1 咸虾

页面使命：
把线下场景、二维码、活动入口、实体物品，转换成一个“大家都在说什么”的即时社交雷达页。

### 页面信息组织要求

首页结构：

1. 顶部左侧标题 `咸虾`，右侧主入口是扫码。
2. 标题下方放搜索和场景筛选 chips，例如餐厅、活动、品牌、办公楼、展会。
3. 首屏可有一个横向滑动的“最近扫过”或“现在最热场景”轻模块。
4. 主体内容统一进入双列瀑布流。

卡片组织规则：

- 第一优先卡片是 `场景摘要卡`，用一句话告诉用户这里大家在聊什么。
- 第二优先卡片是 `热观点卡`，突出高讨论度内容。
- 第三优先卡片是 `活跃分身卡`，让用户发现值得进一步接触的人。
- 第四优先卡片是 `立即发起社交卡`，把场景直接转成意图。
- 同一场景的卡片允许混排，但必须有清晰标签告诉用户这张卡属于摘要、观点还是人物。

交互约束：

- 用户应当可以只靠刷卡片理解一个场景，而不必先点进详情。
- 扫码进入的新场景，默认在卡片流顶部插入该场景的首批摘要卡。
- 咸虾页不承载冗长编辑器，复杂动作统一跳到详情或 `赚闲能`。

### 功能点 1：扫码进入场景话题页

定义：
用户扫一个“龙虾码”后，进入对应场景的公共讨论层，看这个场景里现在有哪些观点、梗、争议、热门对象和活跃分身。

技术细节项：

- 客户端需要相机扫码入口，支持二维码、短链、活动码、邀请码。
- 需要统一 `scan_target` 数据模型，区分餐厅、活动、品牌、群体、商品、人物名片等场景类型。
- 需要场景页本地缓存，避免重复扫码时重新加载全部内容。
- 需要一个 `scene_feed` 聚合结构，承载公开帖子、AI 摘要、情绪标签、热点问题。
- 需要针对无网络或弱网络场景做降级，至少保留最近一次缓存摘要。
- 需要审核和反垃圾入口，避免扫码页变成垃圾信息聚集地。

### 功能点 2：大家都在说什么

定义：
不是直接丢一堆帖子，而是先给用户一个 AI 生成的“场景摘要”，包含正在流行的观点、争议点、共识点和情绪温度。

技术细节项：

- 需要对 `scene_feed` 做主题聚类，至少支持话题聚类、情绪分层、关键词抽取。
- 需要一个摘要管线，把原始讨论转成 `summary_card`、`hot_take_card`、`risk_card`。
- 需要基础情绪分析，识别正向、负向、分裂、中性。
- 需要把 AI 摘要和原始内容做可追溯绑定，点开摘要能回看来源。
- 需要本地 SQLite 表存储场景摘要与过期时间，避免每次重算。
- 需要敏感词和人身攻击的过滤规则。

### 功能点 3：场景里的活跃分身雷达

定义：
用户可以看到在这个场景里最活跃、最专业、最会整活、最值得私聊的分身卡片。

技术细节项：

- 需要 `scene_agent_presence` 数据模型，记录某个分身在某场景里的活跃度、标签、信誉。
- 需要分身公开资料卡，展示身份标签、意图标签、可聊范围、是否允许陌生人 Agent 先聊。
- 需要隐私半径和可见性设置，不允许默认暴露精确位置或真实身份。
- 需要排序策略，至少区分“最热”“最新”“最匹配我”“最可信”。
- 需要跳转到“赚闲能”的陌生社交流程，而不是直接打散信息架构。

### 功能点 4：从场景直接发起陌生社交

定义：
用户在咸虾页看到有意思的人或分身后，可以立刻发起一个意图，比如“交个朋友”“一起吃饭”“聊合作”“求职咨询”。

技术细节项：

- 需要从扫码页一键生成 `intent_draft`，带上场景上下文。
- 需要把场景标签注入匹配引擎，提高命中质量。
- 需要引导用户选择真人先聊、分身先聊、双方分身先聊三种模式。
- 需要跳转到 `赚闲能` 页中的陌生社交撮合链路。
- 需要一个最小风控，阻止骚扰、刷屏、恶意搭讪。

## 3.2 大师

页面使命：
让用户和“各领域大师分身”聊天，既能得到专业帮助，也能得到陪伴式对话体验。

### 页面信息组织要求

首页结构：

1. 顶部标题 `大师`。
2. 标题下方固定一个“最近聊过谁”的横向胶囊条或头像条。
3. 再下方是领域筛选 chips，例如情绪、婚恋、求职、融资、创作、生活。
4. 主内容区统一进入双列瀑布流。

卡片组织规则：

- 第一优先卡片是 `大师人物卡`，展示擅长领域、风格和一句代表性人设。
- 第二优先卡片是 `继续上次话题卡`，帮用户快速恢复熟悉上下文。
- 第三优先卡片是 `问题模板卡`，降低用户开聊成本。
- 第四优先卡片是 `多大师会诊卡` 或 `热门主题卡`，把单点咨询扩展成玩法。
- 卡片高度由信息量决定，大师卡可更高，问题模板卡可更轻。

交互约束：

- 首页优先解决“今天我找谁聊”这个问题，不先展示冗长配置项。
- 用户点进大师详情后，才看到完整资料、历史记录和长期记忆解释。
- 最近聊过谁必须是轻量常驻入口，但不占满首屏。

### 大师产品约束

大师不是用户现场生成的 Agent，而是平台预设好的 `大师资产包`。

固定约束：

- 大师列表由平台预置，不允许用户在 iOS 端新建、删除、编辑大师。
- 用户只能做 `浏览`、`聊天`、`收藏/置顶最近聊过`、`触发多大师会诊`、`清空与某位大师的会话记忆`。
- 大师的人设、故事、portrait、头像、风格字段由外部资产包导入，不在客户端内编辑。
- 你后续提供的真实大师列表，应该被视为内容资产，不是用户数据。
- iOS 端只负责消费、缓存、展示和对话，不负责大师内容创作后台。

### 大师资产包结构

大师页的数据结构直接参考 `../alphane_ai_backend/` 中现有的 `character`、`story` 和导出格式。

导入包建议由以下几部分组成：

1. `master_character`
   - 对齐后端 `Character` 核心字段，用于大师人设和回复风格。
2. `master_stories`
   - 每位大师固定 3-5 个最重要人生故事，对齐后端 `Story` 核心字段。
3. `master_story_beats`
   - 每个故事下保留若干 `story_beats` 或章节摘要，供检索与引用。
4. `master_portrait_assets`
   - portrait、avatar、背景图等展示资源。
5. `master_manifest`
   - 大师所属领域、排序、上线状态、是否 featured、是否允许会诊等平台配置。

资产包格式约束：

- 字段命名尽量对齐后端已有命名，避免 iOS、插件、后台各自发明一套。
- 每位大师必须至少带 `1 个角色主体 + 3-5 个重要故事 + 1 套 portrait/avatar`。
- 故事不是装饰素材，而是大师回答时的核心引用来源。
- 允许后续批量导入新大师，但导入动作属于后台内容运营，不属于客户端功能。

大师页裁剪后的使用原则：

- 每个故事至少要有 `故事标题 + 故事摘要 + 2-6 个 story beats 或章节摘要`。

- 对用户展示时，故事卡片用于建立“这个大师为什么值得聊”的可信感。

### 大师对话请求逻辑

大师对话请求不是裸 user prompt，而是由预设角色字段 + 故事字段 + 用户上下文共同组装。

请求装配顺序：

1. 加载 `master_character` 静态档案。
2. 加载该大师固定的 3-5 个 `master_stories` 摘要。
3. 根据用户问题，从 3-5 个故事中检索最相关的 1-2 个故事及其 `story_beats`。
4. 读取用户与该大师的最近会话、长期记忆、最近目标。
5. 读取当前对话问题、引用消息、最近上下文。
6. 生成本轮的大师回复请求。

请求内容必须至少包含：

- 大师角色身份与领域。
- 大师人格与说话风格。
- 大师与用户的关系设定。
- 大师最相关的人生故事摘要。
- 用户最近问过的主题与未完成事项。
- 当前问题和最近几轮对话。

请求逻辑规则：

- 如果问题命中某个故事主题，优先调用该故事作为回答依据。
- 如果问题没有命中特定故事，也必须遵守大师的人设、价值观和表达风格。
- 如果问题超出 `good_at` 范围或落入 `bad_at`/边界外，系统应让大师显式收敛，不装懂。
- 如果用户连续追问同一主题，系统应优先复用同一故事脉络，保持连续性。
- 如果用户问题适合“先讲故事再给建议”，优先走故事驱动回答。

### 大师对话回复逻辑

大师回复必须体现“完整人设 + 人生故事 + 专业判断”，而不是普通问答机器人。

回复结构建议：

1. 用符合大师 `speech_style` 的开场或承接句回应用户。
2. 判断本轮要不要引用人生故事。
3. 如果引用故事，优先引用一个最相关的故事片段或 `story_beat`。
4. 再给出大师视角的判断、建议、提醒或反问。
5. 必要时生成下一步行动建议。

回复逻辑规则：

- 每次回答都必须服从 `personality_traits`、`personality_mind`、`personality_emotion`、`speech_style`。
- 回答允许带“大师口吻”和人生经验，但不允许捏造未导入的人生履历。
- 大师引用故事时，应像真实人物回忆往事，而不是像数据库检索结果。
- 如果用户需要实操建议，大师不能只讲故事，必须落到行动建议。
- 如果用户需要陪伴，大师可以减少工具化建议，强化共情和个人经历映射。
- 如果用户在同一会话中多次触发某个故事，系统应维护“这个故事已经聊到哪”的连续性。

推荐的回复模式：

- `story_first`
  - 先讲相关经历，再给建议。
- `advice_first`
  - 先给结论，再用故事补充可信度。
- `companion_mode`
  - 以陪伴和共情为主，故事轻引用。
- `mentor_mode`
  - 以判断、拆解和行动项为主。

### 大师故事触发与展示逻辑

故事在大师页有两层作用：`增强列表可信度` 和 `驱动对话质量`。

列表层：

- 大师卡应展示 1 条代表性人生故事钩子。
- 大师详情页应展示 3-5 个重要故事卡。
- 每张故事卡至少展示标题、时期、主题、摘要、代表性收获。

对话层：

- 用户问题进入后，需要先跑 `story relevance` 检索。
- 命中故事后，只把对应故事摘要和少量 beats 注入上下文。
- 如果未命中，也要保留角色主体档案作为固定系统上下文。
- 多大师会诊时，每位大师只带自己相关故事，不共享完整人生故事库。

### 导入与运营逻辑

你后续会直接提供一套 `角色 + 故事 + portrait` 的大师资产包，因此蓝图需要约束 iOS 侧如何消费。

导入规则：

- 导入入口属于后台或开发工具，不属于终端用户界面。
- 导入时按 `master_id` 或 `character_id` 做幂等覆盖。
- 一位大师的资产包需要同时导入角色主体、故事数组和 portrait 资源。
- 导入后客户端只读使用，默认不可在 App 内改写内容资产。
- 允许后续追加新的大师，但已有大师内容更新也走“重新导入资产包”。

### 功能点 1：大师馆首页

定义：
一个按领域分类的专家分身入口，覆盖婚恋、情绪、求职、商业合作、融资、创作、生活决策等。

技术细节项：

- 需要 `master_profile` 数据模型，定义领域、风格、知识边界、人格设定、可用能力。
- 需要 `master_profile` 对齐后端 `character` 核心字段，而不是重新造一套专家 schema。
- 需要分类检索和搜索，支持按领域、人格风格、口碑、最近活跃度筛选。
- 需要卡片式 UI，展示大师头像、擅长主题、最近回答风格、聊天入口。
- 需要支持固定系统 prompt、预设故事资产、可选话题模板。
- 需要区分“真专家映射分身”和“纯虚拟专家分身”两种来源。
- 需要明确大师列表为预设静态目录，不支持用户创建、删除、编辑大师。

### 功能点 2：最近聊过谁

定义：
页面上边栏展示最近对话过的大师，支持快速恢复上下文。

技术细节项：

- 需要 `recent_master_session` 表记录大师 ID、最后消息时间、未读、上次话题。
- 需要本地 SQLite 持久化最近列表和草稿状态。
- 需要支持 pinned masters 置顶。
- 需要在进入会话时加载对应的上下文摘要，而不是从零开始。
- 需要同时记住最近命中的人生故事和当前故事脉络，避免每次重新铺陈人设。

### 功能点 3：大师分身的长期记忆

定义：
大师要“记得我是谁、我之前问过什么、我现在处于什么阶段”，否则体验很快变成一次性问答工具。

技术细节项：

- 需要 `master_memory_note`、`master_conversation_summary`、`user_goal_snapshot` 等记忆结构。
- 需要为每位大师维护独立长期记忆，不同大师不要共享全部隐私。
- 需要在本地存储用户授权的大师记忆范围，并支持用户删除。
- 需要支持摘要压缩，避免上下文无限膨胀。
- 需要支持记忆召回策略，优先召回最近目标、情绪状态、未完成行动项。
- 需要区分 `大师静态人生故事` 和 `大师对用户的动态会话记忆`，二者不能混成一层。

### 功能点 6：大师资产包与故事库

定义：
每位大师由预设的角色主体和 3-5 个最重要的人生故事构成，App 只读消费，不提供端侧编辑。

技术细节项：

- 需要 `master_character_asset`、`master_story_asset`、`master_story_beat` 数据结构。
- 需要支持 portrait、avatar、背景图等资源路径缓存。
- 需要支持导入后本地索引，按大师、领域、故事主题检索。
- 需要允许基于 `character_id/story_id` 做幂等更新。
- 需要让故事字段命名尽量兼容 `alphane_ai_backend` 现有导出格式。

### 功能点 7：大师故事驱动对话

定义：
大师回答用户时，不只是调用人设，而是用“最相关的人生故事”驱动回复的可信度、温度和连续性。

技术细节项：

- 需要 `story_relevance` 检索，把用户问题映射到 3-5 个重要故事中的 1-2 个。
- 需要 `story_snippet` 裁剪逻辑，只注入最相关摘要和 beats。
- 需要请求装配器，把角色字段、故事字段、会话记忆统一组装。
- 需要回复模式路由，例如 `story_first`、`advice_first`、`companion_mode`、`mentor_mode`。
- 需要限制模型不能捏造未导入的大师生平。

### 功能点 4：多大师会诊

定义：
当问题复杂时，允许同时拉入多个大师，例如“求职大师 + 融资大师 + 情绪大师”，形成多分身咨询。

技术细节项：

- 需要多 Agent 编排器，控制谁先说、谁补充、谁总结。
- 需要会话角色定义，区分主持人、大师、用户。
- 需要多分身上下文裁剪，避免 token 爆炸。
- 需要冲突观点合并机制，不能只是多段独立回复拼接。
- 需要本地保存多大师会诊记录，后续可继续。

### 功能点 5：大师导向行动

定义：
大师不仅输出建议，还可以把用户导向下一步动作，例如跳去“赚闲能”发起求职招人或跑腿求助，或者跳去“消息”继续维护熟人关系。

技术细节项：

- 需要 `action_recommendation` 结构，支持 CTA 跳转。
- 需要和其他 Tab 共用深链路由。
- 需要可解释的推荐理由，告诉用户为什么建议去某个功能。
- 需要基础效果跟踪，统计建议是否被采纳。

## 3.3 赚闲能

页面使命：
这是产品主战场。这里承载陌生社交、陌生人分身发现、意图撮合、A2A 预沟通、社交游戏和赛道撮合，但首页组织按 6 条明确赛道展开，而不是按抽象创意方向展开。

### A2A 赛道组织原则

`赚闲能` 的一级组织不是“婚恋/商业/地图/竞技场”等混合概念，而是可比较的 6 条 A2A 产品赛道：

1. 闲置物品买卖
   - 类比 `咸鱼`
   - 买家 Agent 和卖家 Agent 先完成问价、验货、议价、筛选低质量沟通。
2. 技能问答撮合
   - 类比 `evomap`
   - 提问者 Agent 和技能方 Agent 先对齐问题边界、交付方式、是否值得继续聊。
3. 婚恋匹配
   - 男女匹配为主
   - 双方 Agent 先筛价值观、关系期待、见面风险和节奏。
4. 交友匹配
   - 类比 `Soul`
   - 先匹配情绪、兴趣、人格氛围，再决定是否真人接入。
5. 求职招人
   - 类比 `Boss直聘`
   - 候选人 Agent 和招聘方 Agent 先完成岗位理解、履历解释、意向确认。
6. 跑腿求助应答
   - 类比 `RentAHuman`
   - 需求发布者和应答者先通过 Agent 确认任务内容、时间、预算、可靠性。

### 页面信息组织要求

首页结构：

1. 中间黄色大按钮点击后进入 `赚闲能` 主页，视觉上必须最强。
2. 顶部固定区展示当前闲能余额、今日可赚、快捷筛选。
3. 闲能页首屏提供 6 条赛道 chips：闲置物品、技能问答、婚恋、交友、求职招人、跑腿求助。
4. 主内容区统一进入双列瀑布流，不做传统 tab list。

卡片组织规则：

- 第一优先卡片是 `赛道机会卡`，告诉用户这条赛道里发生了什么。
- 第二优先卡片是 `别人的分身卡`，用于发现对象。
- 第三优先卡片是 `双 Agent 破冰卡`，直接展示系统如何替用户先聊。
- 第四优先卡片是 `竞技场/任务/活动卡`，承担好玩和赚闲能。
- 第五优先卡片是 `赛道结果卡` 或 `高价值线索卡`。
- 不同卡片允许高低错落混排，形成逛 feed 的体验，而不是“功能入口九宫格”。

交互约束：

- 任何卡片都应该能把用户往 `human-agent-agent-human` 流程推，而不是只做信息展示。
- 用户刷卡片时应当持续看到“我为什么能在这里赚到闲能”。
- 闲能经济、匹配机会、活动入口、破冰入口必须混排，不要分散到过多二级 tab。
- 商业类高价值卡片可以更克制、更专业；婚恋交友类卡片可以更情绪化、更轻。
- 同一条赛道里，用户必须能清楚看到 `如果不靠 A2A，要多麻烦；用了 A2A，省掉了哪几步`。

### 功能点 1：陌生社交意图市场

定义：
用户进入后先选自己要做哪条赛道，再选具体意图，不先选人。核心赛道是闲置物品买卖、技能问答撮合、婚恋、交友、求职招人、跑腿求助应答。

技术细节项：

- 需要 `social_intent` 枚举和分层分类体系。
- 需要赛道级模板和意图级模板两层结构。
- 需要每种赛道的表单模板，字段随场景变化，比如买卖关注品类/成色/预算，技能问答关注问题范围与交付方式，婚恋关注偏好与边界，招聘关注岗位和履历，跑腿关注时间地点预算。
- 需要 `intent_post` 数据模型，允许公开投放、半公开匹配、定向投递三种模式。
- 需要意图草稿、历史意图、意图状态机。
- 需要客户端卡片流、筛选器、标签体系和推荐排序。

### 功能点 2：human-agent-agent-human 四段式破冰

定义：
这是核心玩法。陌生社交不应该一上来就真人对真人，而是先让双方分身互相摸底、过滤、暖场、探意图，再把真人拉进来。

技术细节项：

- 需要会话模式 `human_only`、`agent_first`、`dual_agent_first`、`human_takeover`。
- 需要 `handoff_rule`，定义什么条件下从 Agent 对话切到真人参与。
- 需要 `consent_gate`，双方都要明确授权真人被拉入。
- 需要 `agent_intro_prompt`、`agent_screening_prompt`、`agent_summary_prompt` 三类提示模板。
- 需要对 Agent 生成内容做审计日志，确保用户能回看“分身替我说了什么”。
- 需要防止 Agent 擅自承诺、擅自泄露隐私、擅自越权的规则引擎。

### 功能点 3：发现别人的分身

定义：
用户看到的不是传统个人资料页，而是“别人愿意拿出来社交的分身卡”。这张卡既有意图，也有人设，也有能力边界。

技术细节项：

- 需要 `agent_public_card` 结构，包含领域、人格标签、聊法、开放时段、期望对象、是否允许分身先聊。
- 需要多场景分身卡，同一个用户在婚恋、工作、合作场景可以是不同面具。
- 需要分身卡的可解释标签，减少“为什么系统推这个给我”的黑盒感。
- 需要卡片曝光、喜欢、略过、屏蔽、举报机制。
- 需要本地缓存已看过的卡片，避免重复刷到同一对象。

### 功能点 4：闲能经济系统

定义：
“赚闲能”不仅是页面名，而是陌生社交和社交游戏的统一货币系统。用户通过参与社交、完成任务、撮合成功来获得闲能，再用闲能解锁更高价值社交机会。

技术细节项：

- 需要 `energy_ledger` 账本，支持收入、支出、冻结、结算、回滚。
- 需要规则引擎定义每日登录、完成破冰、成功撮合、被点赞、参加竞技场等闲能来源。
- 需要定义闲能消耗项，比如发起高价值冷启动、竞拍稀缺机会、解锁高级分身动作。
- 需要反作弊和风控，防止机器人刷闲能。
- 需要可视化能量流向页面，解释赚了什么、花到哪了。
- 需要支持未来接入付费体系，但黑客松版先保留本地规则模拟。

### 功能点 5：六赛道趋势与热点探索

定义：
把 6 条 A2A 赛道做成可探索的趋势层，用户能看到各赛道正在升温的热点、任务密度、机会质量和响应速度。

技术细节项：

- 需要 `a2a_lane`、`lane_heat`、`lane_progress` 三类模型。
- 需要列表化趋势 UI 或赛道热力图 UI，显示当前最热、响应最快、最赚钱、最缺供给的赛道。
- 需要赛道事件机制，比如“本周二手热卖”“热门问答技能榜”“求职季”“跑腿高峰时段”。
- 需要赛道探索任务和奖励。
- 需要把赛道上下文反馈给推荐和匹配系统。

### 功能点 6：A2A 竞技场和社交小游戏

定义：
陌生社交不是只有配对，还可以让分身先打擂台，赢了再进入真人阶段。比如辩论赛、情话对决、商业谈判赛、项目 pitch 对决。

技术细节项：

- 需要 `arena_match`、`arena_round`、`arena_score` 模型。
- 需要至少一套通用对战编排器，支持辩题、回合、评分、结算。
- 需要观众投票和围观入口。
- 需要闲能奖励发放逻辑。
- 需要 AI 裁判或规则评分器，但必须允许人工复核。
- 需要回放摘要，便于用户分享战绩。

### 功能点 7：陌生关系升温与羁绊任务

定义：
陌生社交一旦匹配成功，不能立即坍塌成普通聊天窗口，需要有“从陌生到熟悉”的机制，比如连续 7 天互动任务、双人目标、关系纪念卡。

技术细节项：

- 需要 `bond_level`、`bond_task`、`bond_milestone` 模型。
- 需要在匹配成功后生成初遇纪念卡。
- 需要自动检测关系强度，比如回复频率、情绪稳定性、共同任务完成率。
- 需要关系降温和挽回逻辑。
- 需要支持从“赚闲能”沉淀到“消息”页的线程迁移。

### 功能点 8：赛道撮合结果与结算

定义：
这 6 条赛道最终都不是只聊天，而是要达成结果。产品要能承接交易、应答、接单、配对、入职、服务完成等结果状态。

技术细节项：

- 需要 `lead_pipeline`、`deal_stage`、`match_outcome` 模型。
- 需要记录撮合来源、双方确认、阶段推进、是否真人接手。
- 需要按赛道定义不同结果，例如买卖成交、技能问答成交、婚恋进入线下、交友转熟、招聘进入面试或录用、跑腿任务完成。
- 需要支持“推荐了谁给谁”的审计链。
- 需要支持未来佣金、奖励或积分结算。
- 需要在黑客松版至少实现本地状态流转和结果标记。

## 3.4 消息

页面使命：
熟人关系、长期关系、双人陪伴关系都放在这里。重点是“真人和对偶 agent 一起玩”，而不是单纯 IM。

### 页面信息组织要求

首页结构：

1. 顶部标题 `消息`，右侧可有搜索、发起新会话或筛选入口。
2. 最上方固定一个 `最近聊天` 横向区，放最近活跃联系人。
3. 最近聊天下方是 IM 风格消息列表，按最近活跃、未读、关系状态排序。
4. 点进单个线程后，不是直接只剩气泡时间线，而是先展示卡片化上下文区，再进入聊天时间线。

卡片组织规则：

会话详情页卡片优先级：

- 第一优先卡片是 `关系摘要卡`，说明你和这个人当前关系温度、上次聊到哪。
- 第二优先卡片是 `对人面具卡`，展示你当前对这个人启用的面具和可切换项。
- 第三优先卡片是 `情绪与记忆卡`，展示最近情绪状态、回忆点、未接续话题。
- 第四优先卡片是 `Agent 摘要卡`，告诉用户最近这段关系里发生了什么。
- 第五优先卡片是 `关系事件卡`，例如纪念日、双人任务、关系提醒。

交互约束：

- 消息首页负责“快速找到人”，所以允许保留 IM 语义。
- 消息详情负责“理解这段关系现在是什么状态”，所以必须在时间线前卡片化。
- 熟人社交优先展示关系温度、对人面具和上下文，而不是只看最后一句消息。
- 允许按 `全部 / 熟人 / Agent 活跃 / 待处理` 筛选消息列表。
- 如果某段关系最近需要维护，应在首页列表中被显著提前。

### 功能点 1：熟人聊天主线程

定义：
这是普通熟人消息页，但每个会话背后都允许挂一个对偶 Agent，帮助记忆、暖场、总结和共同玩。

技术细节项：

- 需要 `conversation_thread`、`message`、`participant` 模型。
- 需要消息发送者类型，至少支持 `human`、`agent`、`system`。
- 需要消息模式切换，支持只看真人、展开 Agent、折叠 Agent 摘要。
- 需要本地 SQLite 消息索引、分页、全文搜索。
- 需要草稿、未读、会话置顶、免打扰。

### 功能点 2：对人面具管理

定义：
用户可以针对不同熟人调整自己分身的面具，例如对同事更克制、对朋友更松弛、对亲密对象更柔软。

技术细节项：

- 需要 `per_contact_mask` 或 `conversation_mask_override` 模型。
- 需要把默认面具和对人覆写面具分开存储。
- 需要支持按联系人切换说话风格、边界感、主动性、情绪表达强度。
- 需要在进入会话时显式展示当前面具，避免用户忘记自己对某人设了什么。
- 需要保留面具调整历史，便于回看关系变化。

### 功能点 3：真人 + 双方分身四人同场

定义：
两个真人聊天时，双方分身可以作为陪聊者、解释器、整活工具、辅助决策者同时存在。

技术细节项：

- 需要一个线程内多角色发言模型。
- 需要角色标识和消息样式区分，避免用户看不懂谁在说话。
- 需要谁可以召唤 Agent、谁可以静音 Agent、谁可以要求 Agent 总结的权限规则。
- 需要 Agent 插话频率控制，不然体验会过吵。
- 需要本地会话配置存储。

### 功能点 4：熟人关系养成玩法

定义：
对熟人不是“匹配”，而是“共同维护”。例如早安打卡、双人任务、回忆卡、关系周年、共享梗库。

技术细节项：

- 需要 `relationship_ritual`、`shared_memory_card`、`shared_task` 模型。
- 需要时间驱动任务调度，例如每日提醒、纪念日提醒。
- 需要共同回忆摘要，把长聊天压缩成可回顾的关系时间线。
- 需要分身参与生成纪念内容，但不能伪造真人意图。
- 需要情绪监测，识别关系冷却期并给出维护建议。

### 功能点 5：熟人群聊 + Agent 玩法

定义：
不止一对一。三五个朋友的群聊也可以带分身一起玩，比如做局、投票、角色扮演、复盘、自动总结。

技术细节项：

- 需要 `group_thread` 和群组成员权限模型。
- 需要群内 Agent 角色，例如书记员、气氛组、主持人、提案器。
- 需要群投票、小游戏、自动纪要、行动项提取。
- 需要消息噪音控制，避免群里 Agent 过载刷屏。
- 需要群级别开关，让群主决定是否允许 Agent 常驻。

### 功能点 6：消息里的跨会话记忆与情感连续性

定义：
熟人聊天最重要的是连续性。系统要记得你们上次聊到哪、最近关系状态如何、谁最近情绪低落。

技术细节项：

- 需要 `memory_recall_job`，在进入线程时自动召回关系记忆。
- 需要 `emotion_state_snapshot`，追踪对方和自己最近的情绪走势。
- 需要会话摘要和长程记忆分层存储。
- 需要用户手动纠正记忆，避免 Agent 瞎记。
- 需要本地优先设计，敏感关系数据先落 SQLite。

## 3.5 我的

页面使命：
“我的”不是设置页，而是分身控制台。这里重点展示同步度、人格、记忆、觉醒、统计和隐私边界。

### 页面信息组织要求

首页结构：

1. 顶部区域是用户 profile 和分身核心状态概览。
2. 顶部下方可以有一个轻量级总览卡，例如同步度总分、觉醒度、闲能余额。
3. 主内容区统一进入双列瀑布流。
4. 具体编辑行为，例如资料编辑、人格编辑、记忆编辑、隐私授权，进入详情或 sheet。

卡片组织规则：

- 第一优先卡片是 `同步度卡`，它是“我的”首页最重要的信息对象。
- 第二优先卡片是 `人格与面具卡`，展示当前主面具和关键人格参数。
- 第三优先卡片是 `记忆卡`，让用户看到分身最近记住了什么。
- 第四优先卡片是 `成长统计卡`，展示社交和分身成长轨迹。
- 第五优先卡片是 `隐私与本地数据库卡`，强调本地存储和控制权。
- 这些卡片要像内容 feed 一样可浏览，而不是像系统设置一样一行一行堆叠。

交互约束：

- 用户打开“我的”时，第一感知应该是“我在培养一个数字分身”，不是“我在改系统设置”。
- 高价值状态如同步度下降、记忆冲突、数据库异常，需要作为特殊卡片插入 feed 顶部。
- 编辑入口可以强，但不能破坏首页卡片流的浏览节奏。

### 功能点 1：My Profile

定义：
基础个人资料、对外展示资料、分身公开资料都从这里管理。

技术细节项：

- 需要 `user_profile`、`public_profile`、`agent_profile` 三层资料模型。
- 需要头像、昵称、标签、简介、场景偏好等字段。
- 需要控制哪些字段公开、哪些只给大师看、哪些只给自己分身看。
- 需要本地缓存和编辑草稿。

### 功能点 2：分身同步度仪表盘

定义：
核心指标是“我的分身像不像我、懂不懂我、能不能替我说话”。这是“我的”页最重要的产品资产。

技术细节项：

- 需要 `sync_score` 模型，至少拆成语言风格、价值观一致性、关系记忆、意图理解、边界遵守五项。
- 需要分项评分和总分趋势图。
- 需要同步度训练任务，比如补充资料、纠正分身表达、确认记忆、选择面具。
- 需要错误案例回放，让用户看到分身哪里说偏了。
- 需要本地训练反馈记录。

### 功能点 3：分身觉醒度与人格配置

定义：
把策划案里的觉醒度、人格 DNA、情绪基线、面具系统全部放进“我的”，成为用户长期培养分身的核心界面。

技术细节项：

- 需要 `awakening_level`、`persona_dna`、`emotion_baseline`、`mask_profile` 模型。
- 需要支持多场景面具，例如陌生人、朋友、职场、亲密关系、商务合作。
- 需要人格编辑器和默认模板。
- 需要显示最近一次人格漂移或同步度变化。
- 需要规则校验，防止用户设置互相矛盾的人格参数。

### 功能点 4：记忆宫殿管理

定义：
用户可以看到分身当前记住了什么、忘记了什么、哪些内容可以说、哪些内容必须保密。

技术细节项：

- 需要 `memory_item`、`memory_scope`、`memory_confidence`、`memory_expiry` 字段。
- 需要支持短期记忆、长期记忆、关系记忆、私密记忆分类。
- 需要支持搜索、编辑、删除、加密标记。
- 需要支持“永不外发”“仅自己分身可见”“允许在特定场景使用”等权限设置。
- 需要本地加密存储策略。

### 功能点 5：数据统计与成长回顾

定义：
用户至少能看到这几个维度：社交活跃度、分身出战次数、闲能收支、关系增长、同步度变化。

技术细节项：

- 需要 `daily_stats`、`weekly_stats`、`energy_stats`、`relationship_stats` 模型。
- 需要图表组件和统计缓存。
- 需要成长日记，把关键 milestones 自动串起来。
- 需要支持导出个人年度回顾或阶段回顾。

### 功能点 6：隐私与本地后端控制

定义：
因为 iOS 端要内置轻量本地 SQLite 后端，所以“我的”页要让用户感知到数据真的在本地，且可以管理。

技术细节项：

- 需要本地数据库状态展示，比如数据库大小、最近备份时间、最近清理时间。
- 需要本地数据清理、重建索引、导出、删除账户数据入口。
- 需要敏感记忆和消息的本地加密策略说明。
- 需要未来外部渠道同步开关，比如是否允许 OpenClaw 插件读写某类数据。
- 需要用户授权面板，逐项说明哪些能力会用到哪些数据。

## 4. 底层技术蓝图

## 4.1 iOS 端总体架构

建议目录映射：

- `spare-life-ios-app/App/`
  - TabBar、路由、依赖注入、全局状态
- `spare-life-ios-app/Features/`
  - `XianXia`
  - `Masters`
  - `EarnEnergy`
  - `Messages`
  - `Mine`
- `spare-life-ios-app/Domain/`
  - 用户、分身、消息、意图、关系、闲能、记忆
- `spare-life-ios-app/LocalBackend/SQLite/`
  - SQLite 连接、表定义、查询层
- `spare-life-ios-app/LocalBackend/Repositories/`
  - 会话、消息、记忆、分身、闲能、匹配仓库
- `spare-life-ios-app/LocalBackend/ConversationMemory/`
  - 摘要、召回、关系记忆装配

客户端建议：

- UI 先用 SwiftUI。
- 本地存储核心先用 SQLite。
- 本地状态管理先保持简单，围绕每个 Feature 组织 ViewModel 或 reducer。
- 黑客松阶段先保证本地单机闭环，再接远端能力。

页面组织技术要求：

- 需要一个全局复用的 `WaterfallFeed` 组件，用于 `咸虾 / 大师 / 赚闲能 / 我的` 首页，以及 `消息` 详情中的卡片化上下文区。
- 需要统一的 `FeedCard` 协议或模型，让不同 Tab 的卡片能共享布局和交互规则。
- 需要卡片高度测量和缓存，避免滚动抖动。
- 需要每个 Tab 独立保存滚动位置、筛选条件、已加载游标。
- 需要支持本地优先的 feed 拼装，把 SQLite 中不同表的数据组装成卡片流。
- 需要支持卡片类型注册机制，例如摘要卡、人物卡、行动卡、状态卡、事件卡。
- 需要支持卡片级埋点，至少记录曝光、点击、跳转、轻操作。
- 需要支持卡片混排排序器，统一处理 `相关性 + 时间 + 价值 + 状态`。
- `消息` 首页需要一个 `ConversationHubList` 或等价组件，用于 IM 风格列表和最近聊天区。
- `消息` 的线程详情页需要 `卡片化上下文区 + 聊天时间线` 的双层结构，而不是纯瀑布流，也不是纯气泡流。
- `我的` 的编辑详情页不使用瀑布流，保持表单或编辑器；但其首页入口层仍然是瀑布流卡片。

## 4.3 OpenClaw 渠道插件蓝图

`spare-life-openclaw-plugin/` 应承担的角色：

- 处理外部渠道消息的传入传出。
- 统一不同渠道的 payload。
- 把渠道事件翻译为产品内部事件。
- 把产品内部响应翻译回渠道格式。

建议内部模块：

- `src/inbound/`
  - 解析外部事件，转成统一 `InboundEvent`
- `src/outbound/`
  - 把统一响应转成渠道专属消息
- `src/adapters/`
  - 不同渠道的 adapter
- `src/schemas/`
  - `InboundEvent`
  - `OutboundEvent`
  - `AgentHandoffRequest`
  - `AgentHandoffResult`
  - `SceneScanPayload`
  - `IntentExchangePayload`
- `src/handlers/`
  - 场景扫码处理
  - 陌生人分身破冰处理
  - 消息线程同步处理

插件层至少需要的技术细节：

- 渠道身份映射。
- 消息签名校验。
- 幂等处理。
- 重试与死信。
- 事件时间戳和顺序控制。
- 附件与富文本兼容层。
- 可审计日志。

至少需要以下核心能力：

- 人格模板系统。
- 记忆召回与摘要压缩。
- 意图识别与匹配排序。
- 分身先聊的双 Agent 编排。

最低可行的 Agent 角色：

- `SelfAgent`
  - 代表用户本人
- `CounterpartAgent`
  - 代表对方

  - 代表大师分身
- `GroupAgent`
  - 代表群聊工具型角色

## 5. 黑客松优先顺序建议

如果以“能演示出玩法”为第一目标，建议优先级如下：

1. “赚闲能”页的陌生社交意图市场。
2. 双 Agent 破冰和真人接手。
3. “消息”页的多角色消息线程。
4. “我的”页的分身同步度、人格和记忆管理。
5. “大师”页的单大师聊天。
6. “咸虾”页的扫码进场景摘要。

原因：

- 这 6 个点最能体现 `human-agent-agent-human`。
- 这 6 个点最容易把创意手册中的“好玩”和“能成交”结合起来。
- 这 6 个点足以支撑黑客松 demo。
